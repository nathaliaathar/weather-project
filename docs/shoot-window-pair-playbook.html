Work in this order

Do one step until it works. Do not start Streamlit on day 1. First get status 200 from the forecast notebook. Do not write scoring.py until the sample JSON parses.

Step 1 — Get a free key and install libraries

Your task: make your computer ready to talk to OpenWeatherMap.

How: create a key at home.openweathermap.org/api_keys. Copy .env.example to .env and paste the key. Then pip install -r requirements.txt inside weather-project/.

Who: both · Done when: you have a .env file and pip finished without errors.

Step 2 — Notebook: forecast status 200

Your task: send one forecast request for a real city and see that it worked.

How: open notebooks/01_forecast_api_colab.ipynb. GET https://api.openweathermap.org/data/2.5/forecast with params q, appid, units=metric. Print status_code. Do not use /weather (that is only “now”).

Who: both · Do not build the Streamlit page yet.

Step 3 — Read photographer fields from JSON

Your task: find temperature, wind, clouds, rain chance (pop), and sunset.

How: payload["list"][0] and payload["city"]. Practice offline on data/sample_forecast.json.

Who: both · Done when: you can print city, one slot time, those fields, sunset.

Step 4 — Role A: models.py (sample JSON)

Your task: fill HourlyConditions.from_slot_json and ForecastReport.from_api_json.

How: open photo_planner/models.py next to data/sample_forecast.json. Then remove skip on matching tests.

Who: Role A · Role B waits until field names are frozen.

Step 5 — Role A: validation.py then client.py

Your task: clean city and shoot type, then send the live forecast from Python files.

How: fill normalize_city_name and normalize_shoot_type, then get_forecast in client.py. Return a ForecastReport.

Who: Role A · Done when: pytest for models/validation passes and Tel Aviv works.

Step 6 — Together: score weights on paper

Your task: agree what “good weather” means for each shoot type. There is no single correct formula.

How: for portrait, sunset, and landscape, four numbers (rain, wind, temperature, clouds) that add up to 1.0. Put them in SHOOT_WEIGHTS.

Who: both · Do this before coding photography_score.

Step 7 — Role A: scoring.py

Your task: turn weather into a 0–100 score and a recommended window.

How: fill photography_score, hours_on_date, score_forecast, best_shooting_window. MVP window = the best 3-hour slot. Sample date 2026-09-04 keeps 4 hours.

Who: Role A · This file is the product.

Step 8 — Role B: charts, then the mockup page

Your task: make the result screen match the Page mockup tab.

How: photography_score_chart first. In app.py: three st.metric, one st.success, score chart, then two charts in st.columns(2). Catch WeatherError with st.error. No CSS. No JSON parsing in app.py.

Who: Role B

Step 9 — Test on your computer

Your task: use the app like a photographer, including mistakes.

How: streamlit run app.py. Tel Aviv portrait tomorrow 17:00, a sunset session, a missing key.

Who: B leads, A checks whether scores make photographic sense.

Step 10 — GitHub (no secrets)

Your task: share the code without sharing the API key.

How: docs/DEPLOY.md. Inspect git status before every push.

Step 11 — Deploy and screenshot

Your task: Streamlit Community Cloud, then screenshot score + error.

How: share.streamlit.io → this repo → app.py → secret OPENWEATHER_API_KEY.

Step 12 — OPTIONAL Phase 2

Compare Tel Aviv, Haifa, and Herzliya for the same sunset. Skip until the one-city app is solid. Stub is commented in scoring.py.

Page mockup — what to build

Professional, junior-friendly: one Streamlit page, widgets only, no custom CSS, no extra screens. The theme is already in .streamlit/config.toml. Numbers below are an example from data/sample_forecast.json so you can see the layout. Your live scores will be different.

Design rules Decision first, weather second. One screen: inputs on top, result below. Three charts is enough. Do not dump JSON. Empty and error states are part of the product.
