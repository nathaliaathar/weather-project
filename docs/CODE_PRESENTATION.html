Product idea

This is not a weather app

Weather is the input. The product is a decision for outdoor photographers:

“I have a portrait session tomorrow in Tel Aviv at 17:00. Should I shoot then — or is there a better window?”

City + date + time + type → Forecast → Score 0–100 → Best window + charts

Data flow

From click to chart

  1. app.py stores city, date, time, and shoot type
  2. results.py fetches the forecast via client.py
  3. models.py keeps only the useful fields from each 3-hour slot
  4. scoring.py scores every hour and picks the best session
  5. charts.py draws score, temperature, rain, and heatmap

Keeping HTTP, formulas, and UI apart makes the project easier to explain and maintain.

Score — concept

Photography Score = suitability 0–100

  • 87 means “suitability 87/100”, not “87% chance of a good shoot”
  • Five factors: light, rain, wind, comfort, visibility
  • Each factor becomes a number from 0 to 1 (bad → good)
  • Shoot type changes the weight of each factor

Missing data → status unavailable (not a fake score of 0).
Dangerous weather → status not_recommended.

Score — weights

Shoot type changes priorities

TypePriorityWhy
portraitlight 40%soft light + a comfortable subject
eventrain 35%schedules are hard to move
sunsetlight 55%sun position is the product
landscapelight 45% + visibilityscene and clear air matter

Every weight set sums to 1.0. Constants live in SHOOT_WEIGHTS.

Score — formula

Base score + caps

base = 100 × (w_light·light + w_rain·rain + w_wind·wind
        + w_comfort·comfort + w_visibility·visibility)

final = min(base, cap_light, cap_rain, cap_wind, cap_comfort)

Caps stop one great factor from hiding a serious problem. Example: heavy rain still limits the score even when light looks good.

Score — factors

How each factor becomes 0–1

Light — sun height (lat/lon + time) + clouds. Sunset needs a low afternoon sun; portrait likes golden hour.

Rain — 65% chance + 35% mm in the 3-hour slot. More rain → lower score.

Wind — m/s (and gusts). Calm ≤ 2.5; bad ≥ 12.

Comfort — feels-like 18–26°C = 1.0. Outside that band it fades toward 0°C / 40°C.

Visibility: API metres ÷ 10000.

Score — session

Best window ≠ single best hour

The API sends 3-hour slots. A session also lasts ~3h. So we score the full block:

session = 0.60 × mean + 0.40 × 20th percentile
then limited by the worst rain / wind / comfort cap
  • The 20th percentile pulls the score down if part of the session is weak
  • best_shooting_window tries every consecutive block and keeps the best
  • score_booked_interval scores the photographer’s booked time
Charts

charts.py only draws — it never fetches weather

Score line — burgundy line 0–100; blue shade = best window; orange dashed line = booked time.

Temperature — orange line with °C labels on points.

Rain bars — vertical bars for probability (0–100%).

Heatmap — cities × hours; orange (weak) to sky (strong). Missing scores show “—”, never 0.

Shared look in _compact_layout. Colors: burgundy / orange / sky / ivory.

Talking points

In 30 seconds

  1. We score suitability for a shoot, not just temperature.
  2. Five factors 0–1, weights by shoot type, caps against a misleading average.
  3. We recommend the best ~3h session, not a single peak hour.
  4. Charts only visualize what scoring already computed.
  5. Separate files make the logic easy to present and maintain.
